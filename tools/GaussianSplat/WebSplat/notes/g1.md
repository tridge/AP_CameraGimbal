## Acceptance tolerances v2 (in force; PLAN.md v2.1, 2026-11-08)

Changed from v1 below after stage 0 measured that two identical native baseline runs differ per
view by up to 2.3 dB cold PSNR, 0.21 hot IoU and 3.7 C absolute hot peak error (see "Baseline noise
floor"): the v1 per-view floors for criteria 1 and 5 failed when one baseline run was scored against
the other. Per PLAN.md v2.1, every bound is now taken against the worse of the two baseline runs
(`$WEBSPLAT_DATA/ref/baseline_sh`, `baseline_sh_rep2`), and cold PSNR and hot IoU are judged on their
means only. The numbers are unchanged; `metrics.py compare CAND BASE1 BASE2` implements v2.

| # | criterion | tolerance v2 (candidate vs the worse baseline run) |
|---|---|---|
| 1 | cold PSNR | mean >= worse baseline mean - 1.0 dB |
| 2 | hot PSNR | mean >= worse baseline mean - 1.0 dB; every view >= the worse baseline's PSNR for that view - 2.0 dB |
| 3 | absolute peak error, hot views | median <= worse baseline median + 2.0 C; max <= worse baseline max + 5.0 C |
| 4 | absolute peak error, cold views | median <= worse baseline median + 0.5 C; max <= worse baseline max + 2.0 C |
| 5 | hot-region IoU, hot views | mean >= worse baseline mean - 0.05 |
| 6 | false hot detections | cold views flagged <= worse baseline; false hot pixels <= worse baseline + 50 |
| 7-10 | | unchanged from v1 |

## Acceptance tolerances v1 (written 2026-11-08, before any Brush change)

Reference: the native SH-only baseline, `train.py` on `$WEBSPLAT_DATA/ref/work` without
`--lobe`/`--source-gain` (all other options as run13: 30k iterations, `--holdout 20
--hot-holdout 8`, `--hot-weight 20`, `--hot-delta 10`, `--k 8`). Candidate: the Brush fork trained
on the G1 dataset prepared from the same reconstruction (same chosen frames, same frozen
holdouts, same temperature scale). Both are scored by one script (`test/g1/metrics.py`) from
renders of the frozen holdout views, in scaled units clamped to [0, 1], with train.py's
definitions: hot threshold `hot_c` = median frame maximum + 10 C, `v_hot` its scaled value,
a hot view is a view whose frame maximum exceeds `hot_c`.

Per-view metrics: PSNR (scaled units), true and rendered peak (C), absolute peak error
|rendered - true| (C), hot-region IoU (`gt > v_hot` vs `pred > v_hot`), false hot detection
(a cold view whose rendered peak exceeds `hot_c`), false hot pixels (pixels with
`pred > v_hot` and `gt <= v_hot` within 2 px dilation of no true hot pixel).

| # | criterion | tolerance (candidate vs baseline) |
|---|---|---|
| 1 | cold PSNR | mean >= baseline mean - 1.0 dB; every view >= its baseline - 2.0 dB |
| 2 | hot PSNR | mean >= baseline mean - 1.0 dB; every view >= its baseline - 2.0 dB |
| 3 | absolute peak error, hot views | median <= baseline median + 2.0 C; max <= baseline max + 5.0 C |
| 4 | absolute peak error, cold views | median <= baseline median + 0.5 C; max <= baseline max + 2.0 C |
| 5 | hot-region IoU, hot views | mean >= baseline mean - 0.05; every view >= its baseline - 0.15 |
| 6 | false hot detections, cold views | count <= baseline count; false hot pixels summed over held-out views <= baseline + 50 |
| 7 | targets are numeric, not 8-bit / gamma | ground truth as read by the Brush loss kernel equals the prepared scaled temperature within 2e-5 (worst pixel, every view); a pred = gt image gives L1 < 1e-6 |
| 8 | hot-pixel weighted loss | Brush loss value and d(loss)/d(pred) match a NumPy implementation of train.py's loss (L1 with hot weight + 0.2 SSIM) on test images within 1e-4 relative (value) and 1e-3 relative (gradient, L2 norm of the difference) |
| 9 | export | the exported PLY carries `comment apcg_splat` with `kind: thermal` and the dataset temperature scale; rendering that PLY (gsplat, decoded as the viewer does) vs Brush's own eval render of the same view: PSNR >= 45 dB and peak temperature within 1.0 C per view |
| 10 | browser = native | the worker-hosted wasm build meets 1-6 itself (it is scored separately, not only by the native build) |

Recorded without a pass/fail tolerance: training wall time and peak GPU memory on the laptop
and on the win11 machine, Gaussian count. A full browser run on the laptop must finish without
`device.lost` or allocation failure.

The baseline's own seed-to-seed variation is not known; if a criterion fails narrowly, the
baseline is re-run with another seed before calling the failure (and the spread is noted here).

PLAN.md says these tolerances go in PROGRESS.md: proposal for the coordinator to copy them there.

## Repeat policy (written 2026-11-08 after codex's G1 review, before any repeat run)

Codex's review (REVIEW-g1.md) keeps G1 open: the earlier pass rested on single runs, one of them
(the first laptop browser run, 10 GPU errors) invalid. The result below is decided by this policy.

- Build: the forks at the commits recorded with the results (CubeCL ownership fix, invalidating
  worker); dataset, brush_args.txt and harness unchanged across all repeat runs.
- Runs: N = 5 valid browser runs of 30k iterations on each of the laptop and the win11 machine.
  A run is valid only if the worker disposes cleanly with no GPU error, shader compilation error or
  device loss, the page finishes, and all 13 renders and the PLY are complete (run_browser.mjs exit
  0); invalid runs are counted and reported, their artifacts rejected, and replaced, at most 3 per
  machine (a fourth invalid run fails G1 on that machine).
- Baseline repeats: 3 more train.py SH-only runs on the desktop with the stage 0 command (5 total),
  scored the same way. Bounds stay the v2 bounds (worse of the two frozen baselines), so the 3 new
  baseline runs show how often the reference itself meets them.
- Decision, per machine: every criterion 1-6 and 9 must pass in at least 4 of the 5 runs, and the
  median over the 5 runs of each criterion's statistic must be within its bound. Criterion 3 is
  reported per run and view, alongside the baseline repeats.

## Open issues and what stage 6 still needs

- Memory: with the CubeCL fork the browser stays near the native working set, but CubeCL's exclusive
  page pool still churns (about 100 GB of page allocations per run, now destroyed promptly) and costs
  some speed; upstream fixes belong in wgpu (destroy on drop for unshared buffers) and CubeCL.
- Fragile parts to watch: the `enable subgroups;` text fix and the host's `_initialize` call;
  the lifetime test and the GPU-error invalidation guard the buffer handling. A run with any GPU
  error, shader error or device loss is invalid (worker, page and driver all enforce it).
- Not ported from train.py: spatial pruning to the cylinder and canopy ceiling, the Gaussian cap
  (`--max-splats` only bounds), pose refinement, per-image appearance, the lobe and source gain;
  Brush's own densification, LR schedule, mean noise and Mip 3D filter replace gsplat's.
- Exports: the PLY is built in wasm memory (140 MB) and posted to the page; stage 7 should stream it
  to OPFS. On win11 the harness page disappears right after finishing (all results were written).
- Brush's wasm build has no periodic export or exact resume (codex P1 item 7); the worker's
  `exportPly` gives a restart-from-splats checkpoint.
- The 8-bit `unpack_gt_rgb` (LPIPS path) does not read float targets; LPIPS is native-only anyway.
- Masks with numeric targets are not supported (the mask path converts to RGBA8).

## Laptop WebGPU findings

Probe: `test/g1/probe/` (`node run_probe.mjs TAG [query] [chrome flags]`, Chrome 155, laptop flags
`--use-angle=gl --enable-features=Vulkan --enable-unsafe-webgpu`).

1. Canvas presentation is broken on the laptop NVIDIA (headless): configuring a WebGPU canvas and
   presenting fails in Dawn's Vulkan external-memory import (`Requested allocation size (W*H'*4)
   is smaller than the image requires`, ImportMemory, MemoryServiceImplementationOpaqueFD.cpp:132)
   at every size tried (640x480, 1280x720; GL side pads rows to 16, Vulkan image needs 64), and
   sizes already 64-row aligned (1280x768, 640x512, 1024x1024, 1600x1000) lose the device with
   `vkAllocateMemory failed with VK_ERROR_OUT_OF_DEVICE_MEMORY`. The second failed import also loses
   the device. Format (bgra8unorm, rgba8unorm), alpha mode, `--disable-gpu-compositing`, SkiaGraphite
   and `--enable-dawn-features=...` made no difference; `--use-angle=vulkan` gives no adapter;
   without `--enable-features=Vulkan` the adapter is SwiftShader. Compute is unaffected: f32, f16
   absent, subgroups, atomics, 48 KiB workgroup memory, 512 MiB buffers all work, and rendering to an
   ordinary texture plus `copyTextureToBuffer` readback works at 1280x720, 1600x1000, 1920x1080.
   Workaround: never present a WebGPU canvas on this machine. Train in a worker with no canvas; show
   previews by texture readback into a 2D canvas (or the WebGL viewer).
2. Stock Brush's "every pipeline invalid" on the laptop is a separate bug, not the canvas: wgpu's
   naga WGSL output calls subgroup builtins (`subgroupInclusiveAdd`, `@builtin(subgroup_size)`)
   without `enable subgroups;`. CubeCL picks its subgroup kernels (sort, scan) whenever the adapter
   offers `subgroups`, which Chrome does on the laptop NVIDIA; Dawn rejects the modules
   (`cannot call built-in function 'subgroupInclusiveAdd' without extension 'subgroups'`, visible only
   through `getCompilationInfo()`; the console shows only "invalid due to a previous error").
   Workaround in `app/src/stages/train/brush-worker.js`: prepend `enable subgroups;` to WGSL that uses
   subgroup builtins. Upstream fix belongs in wgpu/naga (or CubeCL); worth reporting.
   win11's adapter also offers `subgroups`; with the workaround neither machine logs shader errors.
3. In wasm, CubeCL's roofline autotune bounds (`cubecl_std::throughput::roofline_bounds`, reached from
   the first `sum` reduce in the loss) read GPU results synchronously and panic ("Failed to read
   tensor data synchronously"). The fork sets the CubeCL autotune level to `Full` in wasm, which
   registers no roofline bounds.
4. Brush in the browser used about 4x the native GPU memory (win11: about 9 GB above the idle
   baseline at 590k splats, native 2.0 GB) and failed on the laptop with
   `VK_ERROR_OUT_OF_DEVICE_MEMORY` from about 4000 iterations (memory swinging 2-7 GB). Buffer
   tracing in the worker (`traceBuffers`) showed the cause: CubeCL's exclusive-page pool frees and
   reallocates pages constantly (about 100 GB of 40-90 MiB pages created in 8000 iterations, plus
   Brush's `memory_cleanup()` after every refine), and wgpu's WebGPU backend drops buffers without
   `GPUBuffer.destroy()` (`impl Drop for WebBuffer` is a no-op), so freed GPU memory waited for the
   JS garbage collector. Forcing GC, fewer autotune samples or compiling autotune out did not help;
   never deallocating pages or skipping the cleanup made pages pile up instead (8 GB by 6000
   iterations as tensors move up page buckets). Fix (CubeCL fork, after codex's review): every
   `WgpuResource` handed out for a pool buffer holds a clone of the buffer's ownership token; a
   deallocated buffer is destroyed only when, right after a queue submit of its stream, nothing but
   the pool's queue holds the token (so all work recorded with it has been submitted, and prepared
   tasks that still hold resources keep it), and then only in `on_submitted_work_done`. Earlier
   attempts destroyed by submit age (after the next submit; after 4): the first produced "buffer
